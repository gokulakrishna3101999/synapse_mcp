# SynapseMCP — Resource Reference (Schema, Vector, Indexes, Sparse Columns, Per-Profile Config)

> **Purpose of this file:** a single reference for every persistence-layer *resource* this
> application depends on — the Postgres database, the `vector` extension, every table/entity, the
> 6 sparse embedding columns, the supplemental HNSW indexes/constraints, Redis, and Lucene — how
> each one is configured per Spring profile (`local`/`dev`/`test`/`prod`), and exactly how the app
> consumes/creates each one at runtime. This is a snapshot of the current codebase (generated by
> reading every `@Entity` class, `src/main/resources/migration/schema.sql`, all five
> `application-*.yaml` files, and the relevant service classes) — regenerate by re-reading those if
> they change. For narrative history/rationale behind these decisions, see `rag_plan.md` Stage 0.5
> and Groomings #90/#91; for full column-level table detail, see `implementation/schema.md`
> (referenced from `~/Documents/schema.md` in this environment).

---

## 1. Resource inventory at a glance

| Resource | What it is | Who creates/manages it | Which profiles |
|---|---|---|---|
| Postgres database (`synapsemcp` / `synapsemcp_test`) | The database itself | **External** — `scripts/init-environment.sh`/`.ps1` locally, Terraform for AWS | All |
| `vector` extension | Postgres extension enabling `vector`/`halfvec` column types | **External** — same as above; Hibernate/the app never enables this itself | All |
| 10 tables (via 10 `@Entity` classes) | The relational schema | **Hibernate `ddl-auto`** (in-app, every profile) | All |
| 6 sparse embedding columns on `chunks` | `embedding_384`…`embedding_3072` | **Hibernate `ddl-auto`** (plain JPA-mapped columns) | All |
| 6 HNSW ANN indexes | `idx_chunks_emb_{384,512,768,1024,1536,3072}` | **`schema.sql`**, applied in-app (every profile) | All |
| 2 CHECK constraints | `chk_model_configs_{chat,embedding}_provider` | **`schema.sql`**, applied in-app (every profile) | All |
| 1 unique index | `uq_knowledge_bases_tenant_name_ci` | **`schema.sql`**, applied in-app (every profile) | All |
| Redis | Embedding/OCR cache, rate limiting | External service; app only connects | All |
| Lucene indexes | Per-knowledge-base BM25 keyword index, on local disk | App creates directories at runtime, no external provisioning | All |

The one thing that stays genuinely external in every profile is the database + `vector` extension —
Hibernate has no mechanism to create a Postgres role/database or run `CREATE EXTENSION` itself.
Everything else (tables, sparse columns, HNSW indexes, CHECK constraints, the unique index) is
handled by the app itself, identically, in `local`/`dev`/`test`/`prod` (Grooming #91) — there is no
per-environment code branching for this, only per-profile *configuration*.

## 2. The 10 tables / entities

| Table | Entity class | Package |
|---|---|---|
| `tenants` | `Tenant` | `com.synapsemcp.tenant` |
| `api_keys` | `ApiKey` | `com.synapsemcp.tenant` |
| `model_configs` | `ModelConfig` | `com.synapsemcp.tenant` |
| `knowledge_bases` | `KnowledgeBase` | `com.synapsemcp.knowledgebase` |
| `knowledge_base_model_configs` | `KnowledgeBaseModelConfig` | `com.synapsemcp.knowledgebase` |
| `documents` | `Document` | `com.synapsemcp.document` |
| `ingestion_jobs` | `IngestionJob` | `com.synapsemcp.ingestion` |
| `chunks` | `Chunk` | `com.synapsemcp.rag.chunk` |
| `mcp_users` | `McpUser` | `com.synapsemcp.mcp` |
| `mcp_user_tenant_links` | `McpUserTenantLink` | `com.synapsemcp.mcp` |

**Consumption mechanism:** every one of these is a plain JPA `@Entity`. There is no migration file
anywhere in this repo — Hibernate's `ddl-auto` (per-profile value, §5 below) generates/validates the
actual `CREATE TABLE` DDL from these classes at every application startup, as part of ordinary
`EntityManagerFactory` bootstrap. Standard JPA annotations cover almost everything: `@Id
@GeneratedValue(strategy = GenerationType.UUID)` (client-side UUID PKs), `@Column(nullable =
false)`, `@ManyToOne`/`@JoinColumn` + `@OnDelete(action = OnDeleteAction.CASCADE)` for FKs,
`@Table(indexes = @Index(...))` for plain B-tree composite indexes, `@CreationTimestamp`/
`@UpdateTimestamp` for timestamps, and `@JdbcTypeCode(SqlTypes.JSON)` for the one `jsonb` column
(`chunks.metadata`). `tenant_id` on `documents`/`ingestion_jobs`/`chunks` is a deliberate exception —
a plain denormalized `UUID` column, not a FK, kept for query-filter performance on the hot retrieval
path (confirmed via `EXPLAIN ANALYZE` to matter for HNSW-index selection, not just style).

## 3. The `vector` extension

Enables Postgres's `vector`/`halfvec` column types and the pgvector ANN index machinery
(`vector_cosine_ops`/`halfvec_cosine_ops`). This is a hard prerequisite for Hibernate's own table
creation — the very first `CREATE TABLE ... vector(384)` statement fails with `type "vector" does
not exist` if the extension isn't already enabled.

**Consumption:** never touched by the app itself, in any profile. Enabled externally, before the app
process is ever started:
- **Locally**: `scripts/init-environment.sh`/`.ps1` runs `CREATE EXTENSION IF NOT EXISTS vector;`
  against both `synapsemcp` and `synapsemcp_test` as part of its Step 3 cleanup.
- **AWS (Phase 3, not yet built)**: Terraform's responsibility — e.g. via the `cyrilgdn/postgresql`
  Terraform provider, or a provisioner step running the same SQL against the RDS endpoint, before
  the EC2-hosted app is started.

If it's missing, the app fails to start immediately (a clean, fast Hibernate/JDBC error) — this is
intentional fail-fast behavior (Stage 0), not something the app retries or works around.

## 4. The 6 sparse embedding columns (`chunks` table)

| Column | Postgres type | Hibernate mapping | ANN index (op class) |
|---|---|---|---|
| `embedding_384` | `vector(384)` | `@JdbcTypeCode(SqlTypes.VECTOR)` `@Array(length=384)` | `idx_chunks_emb_384` (`vector_cosine_ops`) |
| `embedding_512` | `vector(512)` | same, `length=512` | `idx_chunks_emb_512` (`vector_cosine_ops`) |
| `embedding_768` | `vector(768)` | same, `length=768` | `idx_chunks_emb_768` (`vector_cosine_ops`) |
| `embedding_1024` | `vector(1024)` | same, `length=1024` | `idx_chunks_emb_1024` (`vector_cosine_ops`) |
| `embedding_1536` | `vector(1536)` | same, `length=1536` | `idx_chunks_emb_1536` (`vector_cosine_ops`) |
| `embedding_3072` | `halfvec(3072)` | `@JdbcTypeCode(SqlTypes.VECTOR_FLOAT16)` `@Array(length=3072)` | `idx_chunks_emb_3072` (`halfvec_cosine_ops`) |

**Design:** sparse-column, not a single flexible column — only the one column matching the owning
knowledge base's `embedding_dim` is ever populated per row; the other five stay `NULL`.
`embedding_3072` uses `halfvec` (half-precision) instead of plain `vector` because pgvector's HNSW
index hard-caps at 2000 dimensions on the full-precision type — `halfvec` raises that cap to 4000.

**Consumption:**
- **Column creation**: Hibernate `ddl-auto`, same as every other column — these are ordinary
  (if vector-typed) JPA-mapped fields on `Chunk.java`, nothing special about how they get created.
- **ANN index creation**: `schema.sql`, not Hibernate — plain JPA has zero ability to express
  `USING hnsw (... vector_cosine_ops)` syntax, regardless of `ddl-auto` mode.
- **Writing data into them**: `ChunkEmbeddingService`/`ChunkPersistenceService`, at real document
  ingestion time — routes each computed embedding into the one column matching the knowledge base's
  locked-in `embedding_dim` (from `KnowledgeBaseModelConfig`, snapshotted at KB-creation time, not
  the tenant's possibly-since-changed live `model_configs`).
- **Reading from them**: `VectorSearchService`, on every `search`/`ask` call in `vector`/`hybrid`
  mode — an ANN cosine-similarity query (`<=>` operator) against whichever column matches the KB's
  `embedding_dim`, filtered by `tenant_id`/`knowledge_base_id` (both denormalized directly onto
  `chunks` specifically so the planner can consider the HNSW index without a join).

## 5. `schema.sql` — HNSW indexes, CHECK constraints, unique index

**File**: `src/main/resources/migration/schema.sql` (moved into a dedicated `migration/`
subdirectory, not the classpath root — see §6 for why every profile needs
`spring.sql.init.schema-locations` set explicitly as a result).

Three things Hibernate/JPA cannot express under any `ddl-auto` setting, all idempotent SQL:

1. **6 HNSW indexes** — `CREATE INDEX IF NOT EXISTS idx_chunks_emb_N ON chunks USING hnsw
   (embedding_N op_class)`, one per sparse column (§4). Pure performance — without them, vector
   search still returns correct results, just via a full sequential scan (this project's own
   testing found the real-world switchover point somewhere between 15,000 and 50,000 rows per
   knowledge base).
2. **2 CHECK constraints** — `chk_model_configs_chat_provider`/`chk_model_configs_embedding_provider`,
   restricting `model_configs.chat_provider`/`embedding_provider` to their supported allow-lists.
   Expressed as `ALTER TABLE ... DROP CONSTRAINT IF EXISTS ...` immediately followed by an
   unconditional `ADD CONSTRAINT` (not a `DO $$ ... EXCEPTION WHEN duplicate_object $$` block —
   Spring Boot's own SQL-script splitter has no concept of Postgres's `$$`-quoting and fragments a
   DO block's internal semicolons into broken statements; confirmed live, this exact bug broke all
   131 integration tests on the first attempt). Pure defense-in-depth — `ModelConfigService.
   validateProvider()` already enforces the identical allow-list at the application layer, on every
   write path, REST and MCP alike.
3. **1 unique index** — `uq_knowledge_bases_tenant_name_ci ON knowledge_bases (tenant_id,
   lower(name))`, a case-insensitive functional index plain JPA `@UniqueConstraint` cannot express.
   **This one is genuinely load-bearing, not just defense-in-depth**: `KnowledgeBaseService.
   updateKnowledgeBase()` (a rename) has no application-level lock protecting it — its entire
   concurrency-safety story is "pre-check the name, `saveAndFlush()`, then catch this exact
   constraint's violation as the only real backstop against a concurrent duplicate-name race."

**Consumption — identical mechanism in every profile (Grooming #91):** Spring Boot's own built-in
deferred SQL initialization (`spring.jpa.defer-datasource-initialization: true` +
`spring.sql.init.mode: always` + `spring.sql.init.schema-locations: classpath:migration/schema.sql`)
runs this file automatically, immediately after Hibernate's own `ddl-auto` step completes, on every
single application context startup. For `test` specifically (`ddl-auto: create-drop`, a fresh schema
every run), this re-applies every time — this was the deciding reason `schema.sql` couldn't be a
purely external, run-once script: nothing external can hook into the in-JVM moment right after a
fresh `create-drop` schema appears. Every statement here is safe to re-run indefinitely — after the
first real run, this whole file is a fast no-op on every subsequent startup.

## 6. Per-profile configuration — the five `application-*.yaml` files

| Setting | `local` | `dev` | `test` | `prod` |
|---|---|---|---|---|
| File | `src/main/resources/application-local.yaml` | `application-dev.yaml` | `src/test/resources/application-test.yaml` | `application-prod.yaml` |
| Database name | `synapsemcp` | `synapsemcp` | `synapsemcp_test` (isolated) | `synapsemcp` |
| `spring.jpa.hibernate.ddl-auto` | `update` | `update` | `create-drop` | `update` (Grooming #91 — was `validate`) |
| `spring.jpa.defer-datasource-initialization` | `true` | `true` | `true` | `true` |
| `spring.sql.init.mode` | `always` | `always` | `always` | `always` (Grooming #91 — was `never`) |
| `spring.sql.init.schema-locations` | `classpath:migration/schema.sql` | same | same | same |
| Redis key prefix (`synapsemcp.redis.key-prefix`) | `synapsemcp` | `synapsemcp` | `synapsemcp_test` | `synapsemcp` |
| `REDIS_HOST`/`REDIS_PORT` default | none (must be set) | `localhost`/`6379` | none (must be set) | none (must be set) |
| `DB_CONNECTION_TIMEOUT` default | `3000` ms | same | same | same |
| `DB_LOCK_TIMEOUT` default | `5s` | same | same | same |
| `REDIS_CONNECT_TIMEOUT`/`REDIS_TIMEOUT` default | `5s` each | same | same | same |

**What this table means in practice:**
- Every profile now applies `schema.sql` itself, in-app — there is no profile where a separate
  external pipeline stage is required to create the HNSW indexes/CHECK constraints/unique index.
- The database + `vector` extension are the one thing that stays external in every profile
  (§1, §3) — that responsibility doesn't show up in this table because it's not a Spring property
  at all, it's a precondition the orchestration layer (a script locally, Terraform for AWS) must
  satisfy before the app process is even started.
- `test`'s `create-drop` is the only profile where the base tables themselves are destructively
  recreated on every run — by design, so every `*IntegrationTest` run gets a genuinely fresh
  schema, and only ever against the isolated `synapsemcp_test` database, never `synapsemcp`.
- `local`/`dev`/`prod` all use `update` — additive/evolving only, never drops existing tables,
  columns, or rows, regardless of how many times the app restarts.

## 7. Other runtime resources (briefly, for completeness)

- **Redis** — not app-managed at all (no schema/index concept); the app only ever connects to it.
  Used for: embedding cache (7-day TTL, `ChunkEmbeddingService`), OCR/extraction cache (24-hour TTL,
  `ExtractionCacheService`), and Bucket4j-backed per-tenant/per-provider rate limiting
  (`ProviderRateLimiter`). Isolated between `test` and every other profile by key prefix
  (`synapsemcp:*` vs `synapsemcp_test:*`), not by a separate Redis database index — same physical
  Redis instance/index 0 in every profile including `test`.
- **Lucene** — one BM25 keyword-search index directory per knowledge base, created by the app at
  ingestion time, never pre-provisioned. Base directory is `synapsemcp.lucene.base-dir` (defaults to
  `${java.io.tmpdir}/synapsemcp/lucene-indexes` if unset; `init-environment.sh` exports
  `SYNAPSEMCP_LUCENE_BASE_DIR` explicitly for local runs). Lives entirely on local disk — a known,
  still-open Phase 3 design question is how this behaves the moment there's more than one app
  instance (a PVC-per-pod or rebuild-on-start strategy), not yet decided.

## 8. Startup sequence, end to end (every profile)

```
[external, before the app process starts]
   Database (synapsemcp / synapsemcp_test) exists
        │  scripts/init-environment.sh/.ps1 (local)  ·  Terraform (AWS, Phase 3)
        ▼
   `vector` extension enabled on that database
        │
        ▼
[in-app, every startup, every profile]
   HikariCP connects
        │
        ▼
   Hibernate `ddl-auto` creates/validates/recreates the 10 tables
   (including the 6 sparse embedding columns) from the `@Entity` classes
        │
        ▼
   Spring Boot's deferred SQL init applies `schema.sql`:
   6 HNSW indexes + 2 CHECK constraints + 1 unique index
        │
        ▼
   Application ready — /actuator/health reports UP
```

If any external prerequisite (database, `vector` extension) is missing, the app fails fast and
cleanly at the HikariCP-connect or first-`CREATE TABLE` step — standard Spring Boot fail-fast, no
custom retry/self-heal loop by design (Stage 0). There is no in-app code path left anywhere that
tries to create the database, the role, or the extension itself.
