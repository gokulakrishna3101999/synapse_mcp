## Phase 2 — MCP Integration & API Management

## Stage 1: MCP Auth & Server Implementation

> **✅ Decision (Grooming #1 — Transport Mechanism):** The MCP server will exclusively use the **HTTP (SSE)** transport. Since the app is designed to run as a multi-tenant web service (both locally and in the cloud), exposing it as a long-lived HTTP server is the most robust and idiomatic approach. `stdio` will not be implemented to avoid treating the web application as a background CLI script.
>
> **✅ Superseded (Grooming #17, implementation session, `plan.md` §9):** Built against **Streamable HTTP**, not SSE. Found while researching the actual `org.springframework.ai:spring-ai-starter-mcp-server-webmvc:2.0.0` starter (the version matching this project's exact Spring AI 2.0.0 pin) that the MCP ecosystem has moved on since Grooming #1 was written: the current starter's `spring.ai.mcp.server.protocol` property treats `SSE` as **deprecated**, with `STREAMABLE` as the current spec's recommended replacement — both remain HTTP-based (not `stdio`), so Grooming #1's actual rationale ("long-lived HTTP server, not a background CLI script") is unaffected either way. User confirmed building against Streamable HTTP rather than the now-deprecated path, asked rather than assumed since this directly contradicts an explicit, numbered decision.

> **✅ Decision (Grooming #11 & #12 — MCP Authentication Flow):** The MCP server will use a dedicated **Username and Password** authentication model (via HTTP Basic Auth) instead of requiring AI clients to manage raw Tenant API Keys. AI clients (like Claude Desktop) will connect to the SSE endpoint using `Authorization: Basic <base64>`. A new open REST endpoint (`POST /api/v1/mcp-users/register`) will allow humans to register these MCP user accounts.

> **✅ Decision (Grooming #13 — Tool Access Control & Tenant Linkage):** When an MCP user authenticates, if their account is not yet linked to a tenant, an MCP interceptor will block all tools EXCEPT `create_tenant`. When they call `create_tenant`, the system will provision the tenant, generate the API key, and permanently save the `tenant_id` on the user's `mcp_users` record. For all subsequent tool calls, the MCP layer will automatically inject this `tenant_id` into the `TenantContext`, allowing seamless consumption of all RAG tools without the AI ever needing to handle the raw API key.

> **✅ Decision (Grooming #14 — Link at Registration):** To allow humans who already created a tenant via the REST API to use MCP without creating a second duplicate tenant, the registration endpoint will accept an optional `api_key`. If provided, the system validates the key, extracts the existing `tenant_id`, and immediately saves it to the new `mcp_users` row. This strictly prevents raw API keys from ever being passed through AI chat prompts.

> **✅ Decision (Grooming #15 — Rate Limiting on MCP User Registration):** `POST /api/v1/mcp-users/register` is open/unauthenticated and is the actual repeatable step an abuser needs (each registered user can only ever link to one tenant, per Grooming #13/#16 below — so registration volume, not tenant-linking, is the real abuse surface for MCP-side tenant creation). It reuses the same per-IP fixed-window limiter pattern as `TenantCreationRateLimitFilter` (`plan.md` §9): **5 requests/hour/IP**, fails **open** if Redis is unreachable, keyed on `request.getRemoteAddr()` (not `X-Forwarded-For`, for the same spoofing reason as the REST limiter). This also protects the endpoint's `api_key`-validation branch from being used to brute-force/enumerate real API keys. No separate rate limit is placed on the `create_tenant` MCP tool itself — it is already self-limiting to one successful call per linked user (Grooming #13), so limiting it further would only add friction to legitimate retry-after-failure without closing any real gap.

> **✅ Decision (Grooming #16 — Atomic Tenant Linkage, Race-Condition Guard):** The interceptor's "is `mcp_users.tenant_id` null?" pre-check (Grooming #13) is a read, not a lock — two concurrent `create_tenant` calls from the same not-yet-linked user could both pass it before either commits, each provisioning a real tenant + API key, with only one able to win the link. To close this: tenant creation, API-key issuance, and the conditional linking update are all executed inside **one `@Transactional` boundary** — `UPDATE mcp_users SET tenant_id = :newTenantId WHERE id = :mcpUserId AND tenant_id IS NULL`. If that update affects 0 rows (another concurrent call already linked this user), the MCP tool handler throws, and Spring's transaction manager **rolls back the entire transaction** — the tenant and API-key inserts are undone as part of the same rollback, never committed in the first place. This is a plain transactional rollback, **not** a separate compensating delete step, so no tenant-deletion capability needs to exist anywhere else in the system for this path. The call returns the same explicit "already linked to tenant X" error as a normal duplicate `create_tenant` call — the user is left with exactly one tenant either way, and nothing is ever persisted for the race loser.

> **✅ Decision (Grooming #18 — Stage 1 implementation session, `plan.md` §9):** Several concrete implementation choices made while building Stage 1, none previously specified: **(1)** the Lua-script fixed-window rate-limiting logic (Grooming #15) was extracted into a new shared `com.synapsemcp.common.FixedWindowRateLimiter` component once a second real caller needed it, rather than copy-pasting `TenantCreationRateLimitFilter`'s script a second time - that filter was refactored to use the same component, with no behavior change (confirmed via its existing test suite, unchanged). **(2)** `McpToolAccessDeniedException` (a plain `RuntimeException`) is the MCP-transport-specific error type thrown by the tool-access aspect and the tenant-linking service - the transport-agnostic counterpart to REST's `ApiException`, which carries an `HttpStatus` that has no meaning in an MCP tool-call context. No separate JSON-RPC error-translation adapter was built for Grooming #8 beyond this: confirmed via the real MCP Java SDK's own decompiled `AbstractSyncMcpToolMethodCallback.createSyncErrorResult(Exception)` that any exception thrown from inside an `@McpTool` method is already caught by the framework and surfaced as a clean tool-level error result - this exception type only needed a message safe to show a client directly, not a bespoke translation layer. **(3)** The MCP interceptor (Grooming #13) is implemented as a Spring AOP `@Aspect` (`McpToolAccessAspect`, `@Around("@annotation(org.springframework.ai.mcp.annotation.McpTool)")`) rather than a request-level `HandlerInterceptor` the way REST's `TenantOwnershipInterceptor` is - `@McpTool`-annotated methods are plain Spring bean methods invoked via the SDK's own reflection-based dispatch, not routed through Spring MVC's handler-mapping machinery, so a `HandlerInterceptor` has no equivalent hook point here. Confirmed AspectJ auto-proxying works with zero additional configuration: `aspectjweaver` was already transitively present on the classpath (unrelated to this session's own additions), and Spring Boot's `AopAutoConfiguration` auto-enables `@EnableAspectJAutoProxy` whenever it detects that class - no `spring-boot-starter-aop` dependency was needed.

- [x] Create `mcp_users` table: `id`, `username` (UNIQUE), `password_hash`, `tenant_id` (Nullable FK), `created_at`. Like every other table, this is a JPA `@Entity` realized via Hibernate `ddl-auto` — no separate migration file (`rag_plan.md` Stage 0.5 / `plan.md` §9, 2026-07-16).
- [x] Implement open REST endpoint: `POST /api/v1/mcp-users/register`.
  - JSON body: `{ "username": "...", "password": "...", "apiKey": "..." (optional) }` — camelCase, matching this project's existing JSON-field convention (`chatApiKey`/`embeddingApiKey` etc.) rather than this section's own snake_case example.
  - Hashes password with **`BCryptPasswordEncoder`** (Spring Security's adaptive/salted default) — deliberately **not** the fast `SHA-256` scheme `rag_plan.md` Stage 0 uses for `api_keys.key_hash`. API keys are high-entropy random secrets where a fast hash is fine; human-chosen passwords need a slow, salted algorithm to resist offline brute-forcing. If `api_key` is present, validates it against `api_keys` table and saves the associated `tenant_id` to the new user.
  - Per-IP rate limited: 5 requests/hour/IP, fail-open on Redis outage (Grooming #15).
  - **User-confirmed choice (asked, not guessed, since this section left it unspecified):** a supplied-but-invalid `apiKey` rejects the whole registration with `422` rather than silently registering an unlinked account.
- [x] Add MCP Java SDK and configure **Streamable HTTP** transport (Grooming #17 — supersedes this line's original SSE/`WebMvcSseServerTransport` wording; built via `org.springframework.ai:spring-ai-starter-mcp-server-webmvc:2.0.0`'s auto-configuration, `spring.ai.mcp.server.protocol: STREAMABLE`, default endpoint `/mcp`).
- [x] Configure Spring Security to secure the MCP transport with HTTP Basic Auth against the `mcp_users` table (path is a single `/mcp` endpoint, not separate `/mcp/sse`/`/mcp/message` paths — a consequence of Streamable HTTP superseding SSE, Grooming #17). Two ordered `SecurityFilterChain` beans: one matched only to `/mcp` requiring Basic Auth, a lower-priority catch-all permitting every other path through unchanged — `/api/v1/**`/`/actuator/**` remain governed entirely by the pre-existing hand-rolled filters, zero behavior change. `ApiKeyAuthenticationFilter` (REST's own bearer-token filter, ordered well before Spring Security's chain) gained an explicit `/mcp` bypass — without it, every MCP request would have been rejected `401` by the wrong auth mechanism before Spring Security ever ran.
- [x] Implement MCP Interceptor (built as a Spring AOP `@Aspect` matched to `@McpTool`-annotated methods, since that's the actual mechanism the real SDK/Spring AI annotation-scanning autoconfiguration provides — not a request-level interceptor the way REST's is):
  - If `mcp_users.tenant_id` is null, block all tools except `create_tenant`.
  - If `mcp_users.tenant_id` is NOT null, inject it into `TenantContext` for the duration of the tool execution.

### Usage Flow: Registration & Tenant Linkage
1. **Scenario A (Brand New User):** Human calls `POST /register` with just `username/password`. They configure their AI client with these credentials. The AI connects, sees the tenant is missing, calls the `create_tenant` MCP tool, and the system securely links the new tenant to the user behind the scenes.
2. **Scenario B (Existing REST User):** Human already has an API key from Phase 1. They call `POST /register` with `username/password` AND their `api_key`. The system links their existing tenant. They configure their AI client, and the AI immediately has access to all tools (`ask`, `search`, etc.) without ever calling `create_tenant`.

## Stage 2: Tool Definitions (Official MCP Java SDK)

> **✅ Decision (Grooming #2 — Tools vs REST Layering):** MCP tools will **directly invoke the underlying domain services** (e.g., `TenantService`, `RagAnsweringService`). This completely bypasses the REST Controllers, avoiding HTTP loopback overhead and aligning with idiomatic Spring Boot architecture. The REST layer and the MCP layer will both act as equal-peer consumers of the core services.

> **✅ Decision (Grooming #4 — Long-Running Ingestion over MCP):** AI clients will be explicitly guided on how to handle async tasks. The MCP `ingest` tool description will include an explicit system prompt instruction: *"This tool returns immediately with a Job ID. You MUST use the job_status tool every 5 seconds until the job completes."* This prevents AI hallucinations regarding job completion.

> **✅ Decision (Grooming #7 — Tool Schema Generation):** All MCP tool inputs will be defined as standard Java `record` classes. We will rely on the official MCP SDK and Spring's Jackson integration to automatically generate the strict JSON schemas from these records, preventing manual schema drift.
>
> **✅ Superseded (Grooming #19, Stage 2 implementation session, `plan.md` §9):** Several findings from actually building the remaining twelve tools, none previously specified or (in two cases) directly contradicting a written decision above:
> **(1) Grooming #7 superseded - flat scalar params, not a wrapping record.** Empirically tested (compiled a probe against the real `spring-ai-mcp-annotations:2.0.0` jar and called its `McpJsonSchemaGenerator.generateForMethodInput` directly) that a tool method taking **one record parameter** produces a **nested** schema - the record's fields end up wrapped under a single property (e.g. `{"arg0": {"query": ..., "topK": ...}}`), not directly callable the way a normal tool argument object should be. A method taking **multiple flat `@McpToolParam`-annotated scalar parameters** (matching `create_tenant`'s existing Stage 1 pattern) produces the flat, directly-callable schema real MCP clients expect. A second probe confirmed `List<record>` parameters (needed for `ask`'s `history` and `evaluate`'s `queries`) schema cleanly as a top-level array-of-objects property - only a *lone* top-level record parameter has the nesting problem. All twelve tools use flat parameters, building the corresponding existing domain request record (`SearchRequest`/`AskRequest`/`EvaluateRequest`/`ConfigureModelRequest`) internally before calling the domain service - no new duplicate DTOs. Parameter names are **camelCase** (`knowledgeBaseId`, `topK`, `contentBase64`), matching the camelCase-over-snake_case precedent Stage 1 already set for the registration endpoint's JSON body, not this document's own snake_case prose examples.
> **(2) Document-count/status-summary rollup (`get_tenant`/`list_knowledge_bases`) uses a single `GROUP BY` query, not the `IngestionMetrics` per-status-loop precedent** - one new `DocumentRepository` JPQL query (`GROUP BY knowledge_base_id, status`, plus a single-KB variant for `create`/`update`), avoiding up to 40 queries for a 10-KB tenant. New `DocumentStatusSummary` record (`pending`/`indexing`/`ready`/`failed` + `total()`/`plus()`) folds the query result.
> **(3) `list_knowledge_bases`' rollup enriches the shared REST contract, not an MCP-only wrapper** - `KnowledgeBaseResponse` gained a `documentStatusSummary` field, populated inside `KnowledgeBaseService` itself (the one method both REST's `GET /api/v1/knowledgebase` and the MCP tool call) - additive, non-breaking for existing JSON clients, one code path instead of two.
> **(4) Grooming #8's "error translation adapter" resolved the same way Stage 1's Grooming #18 already resolved it - no new adapter needed.** Confirmed `ApiException`'s constructor calls `super(detail)`, so `getMessage()` already returns exactly the client-safe text (e.g. `"knowledge base not found"`), never the `HttpStatus`/title - combined with the MCP SDK's own confirmed behavior of catching any exception thrown from an `@McpTool` method and surfacing it as a clean tool-level error, every domain service's `ApiException` propagates straight out and displays cleanly with zero extra code. The one genuinely new piece: a small `McpToolInputs` helper catches `IllegalArgumentException` from bad `UUID.fromString`/`SearchMode.fromValue` input and rethrows as a client-safe `ApiException`.
> **(5) `ingest`'s dual input shapes required a real, previously-nonexistent refactor of `DocumentUploadService`.** It was hard-tied to `MultipartFile` - no byte[]-native entry point existed despite `rag_plan.md` Grooming #28 describing the intended `(byte[], mimeType, filename)` triple in prose. Refactored into a shared private `upload(tenantId, knowledgeBaseId, byte[] content, filename, mimeTypeOverride)` core (`mimeTypeOverride == null` runs Tika detection, non-null skips it); `uploadDocument(MultipartFile)` becomes a thin adapter, and two new public methods (`uploadBytes` for the file-bytes shape, `uploadRawText` for the raw-text shape, defaulting a blank filename to a synthetic `untitled.md`) serve the MCP tool. Behavior-preserving - the existing `DocumentUploadServiceTest` suite passed unchanged. Using test-scope `MockMultipartFile` from production code (the other option surfaced) was rejected as a smell.
> **(6) `RequestBodySizeLimitFilter` now exempts `/mcp`, the same way it already exempted the REST document-upload path.** The `ingest` tool's Base64 `content_base64` shape has no multipart resolver to stream/cap it, so without this exemption the filter's 1MB default would silently cap it far below the REST upload's 20MB. `IngestMcpTool` enforces its own explicit size check against the same `spring.servlet.multipart.max-file-size` config value on the decoded byte length instead - verified live with a real ~2MB raw-text `ingest` call over a genuine HTTP socket (not a mocked request), not just the filter's own unit test.
> **(7) SpotBugs found a real, if initially puzzling, `EI_EXPOSE_REP2` finding on five new/modified constructors** (`CreateKnowledgeBaseMcpTool`, `DeleteKnowledgeBaseMcpTool`, `ListKnowledgeBasesMcpTool`, `UpdateKnowledgeBaseMcpTool`, `TenantService`) for storing a `KnowledgeBaseService` reference from a **public** constructor. Root-caused empirically (toggled one constructor's visibility and reran `spotbugs:check` to confirm): `KnowledgeBaseController`'s own existing, already-clean constructor stores the identical `KnowledgeBaseService` reference but is **package-private** - SpotBugs' `MALICIOUS_CODE` category only flags a constructor callable by code in *any* package. Fixed by making all five constructors package-private (matching `KnowledgeBaseController`'s and most of this codebase's own existing convention already) - Spring's reflection-based DI doesn't care about constructor visibility, confirmed via a clean recompile and passing test suite.

## Stage 3: Caching & Rate Limiting (Redis)

> **✅ Decision (Grooming #3 — Rate Limiting Library):** We will use **Bucket4j** (backed by Redis) for per-tenant/per-provider rate limits. The advanced token-bucket features provided by Bucket4j are necessary for robust rate limit enforcement, justifying the extra dependency.

> **✅ Decision (Grooming #5 — Rate Limiting Enforcement Point):** Since MCP tools bypass REST controllers to call domain services directly, Bucket4j rate limiting MUST be implemented as a Spring AOP Interceptor (`@Aspect`) directly on the **Domain Service layer**. This guarantees that both REST traffic and MCP traffic consume from the same token buckets and are limited equally.
>
> **✅ Decision (Grooming #20, Stage 3 implementation session, `plan.md` §9):** Three points this stage's own checklist left explicitly open, confirmed with the user before writing any code, plus two real bugs found and fixed live:
> **(1) Limit size: 60 requests/minute per tenant per provider** (Bucket4j `Bandwidth.simple(60, Duration.ofMinutes(1))` - a continuous/greedy refill, not a fixed window; matters for how you read any test timing against it).
> **(2) Bucket granularity: separate buckets per (tenant, provider, chat-or-embedding)`, not one combined bucket per (tenant, provider)`** - a tenant's heavy ingestion (embedding calls) can't starve their own Q&A (chat calls) sharing the same provider string, and vice versa. New `RateLimitKind` enum (`CHAT`/`EMBEDDING`).
> **(3) Redis-down behavior: a conservative local (in-JVM) fallback limiter (10/minute, deliberately stricter than the 60/minute Redis-backed limit), not fail-closed** - keeps `ask`/`search`/`ingest` alive through a Redis blip. Explicitly documented as a deliberate *exception* to this codebase's otherwise-universal Redis-fail-open convention (Grooming #68) - rate limiting is the only guard against runaway provider cost, unlike every existing fail-open cache/filter, which only ever risks extra latency or a temporary unlimited window on an *unauthenticated* endpoint.
> **(4) One self-invocation snag, resolved before writing code:** of the six real chat/embedding-provider call sites (`RagAnsweringService.ask`/`askStream`, `LlmRerankerService.rerank`, `VisionTranscriptionService.transcribe`, `ChunkEmbeddingService.embed`, `KnowledgeBaseService.createKnowledgeBase`), the sixth's actual provider call lives in a *private* `probeEmbeddingDimension` helper invoked via self-invocation from `createKnowledgeBase` - Spring AOP proxies can't intercept private methods, and self-invocation bypasses the proxy regardless of visibility. `@RateLimited` is placed on the public `createKnowledgeBase` entry point instead.
> **(5) One behavior-change fork asked and confirmed via `AskUserQuestion`:** `LlmRerankerService.rerank` is documented as "deliberately fail-open" (any provider/parsing failure silently falls back to unreranked order) - since `@RateLimited`'s aspect wraps the whole method from outside its own try/catch, a rate-limit denial would otherwise break that guarantee. **User confirmed: a rate-limit denial on reranking is a hard `429`, same as every other `@RateLimited` method** - not silently absorbed - since a caller who wants to avoid this can pass `rerank=false` to stay on vector/keyword-only retrieval, which never touches a chat provider at all. (`VisionTranscriptionService.transcribe`'s callers, `PdfExtractor`/`ImageExtractor`, already catch broadly around their own vision call for their own existing fallback-to-library-extraction behavior, so a rate-limit denial there is absorbed for free, no extra design decision needed.)
> **(6) Two real bugs found live and fixed, not merely designed around:** First, an early `RateLimitConfig` extracted a native Lettuce connection from a single `LettuceConnectionFactory.getConnection()` call at bean-creation time and held onto it - that method returns a request/operation-scoped wrapper Spring's own lifecycle management can close, and once it did, every rate-limit check silently fell back to the local limiter for the rest of the app's life (`RedisException: Connection is closed`). Fixed by giving `RateLimitConfig` its own standalone `RedisClient`, built directly from `spring.data.redis.host`/`port` with Lettuce's own default (far more generous) command timeout - this app's shared client deliberately uses a tight 1-second timeout tuned for its other, fail-open Redis usage, the wrong setting for Bucket4j's connection pattern. Second, `RateLimitAspect`'s own provider-resolution lookup (needed before `createKnowledgeBase`'s method body even runs) initially treated a missing tenant model config as "should be impossible" and threw a generic `IllegalStateException` - but that's a real, expected, client-facing `422` case `KnowledgeBaseService` itself already handles; fixed to throw the identical `ApiException` the method's own body would have thrown moments later.

- [x] Embedding cache (`ChunkEmbeddingService`) reviewed for hit-rate; add metrics — `synapsemcp.embedding.cache` Counter, tagged `result=hit|miss`, following `IngestionMetrics`'s existing pattern.
- [x] OCR cache (`ExtractionCacheService`) reviewed for hit-rate; add metrics — `synapsemcp.extraction.cache` Counter, tagged `result=hit|miss` and `cache=<namespace>` (`pdf-extract`/`image-extract`).
- [x] Per-tenant rate limiting: token-bucket in Redis via Bucket4j, keyed by `tenant_id + provider + chat-or-embedding` (Grooming #20) — separate buckets per provider *and* per usage kind.
- [x] Rate-limit headers on REST responses (`X-RateLimit-Remaining`, `Retry-After`); structured MCP errors on limit breach — `X-RateLimit-Remaining` via a new `RateLimitContext`/`RateLimitHeaderFilter` pair (mirroring `TenantContext`'s ThreadLocal shape); `Retry-After` via a new `ApiExceptionHandler` handler mirroring the existing `handleLockTimeout` precedent; MCP gets the same clean tool-level error every other `ApiException` already produces, no new code needed there.

## Cross-Cutting Concerns (Mapped from Master Plan)

> **✅ Decision (Grooming #8 — Error Translation):** Domain services throw standard Java exceptions. The MCP layer MUST implement an error-handling interceptor/adapter that catches these domain exceptions and translates them into proper MCP/JSON-RPC error codes (just as the REST layer translates them into RFC 7807 Problem Details). The SSE connection must not crash on a domain error.

> **✅ Decision (Grooming #9 — Observability & MDC):** The MCP HTTP filter chain must generate a Correlation ID for every incoming request and inject it into the SLF4J MDC, exactly like the REST layer. This ensures all logs generated by MCP tool invocations are fully traceable.

> **✅ Decision (Grooming #10 — Metrics):** The MCP layer must emit Micrometer metrics for tool invocation counts, tool execution latency, and Bucket4j rate-limit rejections.
>
> **✅ Decision (Grooming #21, follow-up implementation session, `plan.md` §9):** One genuine fork asked and confirmed via `AskUserQuestion` before writing code: should a tool call **blocked** by tenant-linking or rate limiting still count as a recorded invocation? **User confirmed: yes — every call attempt is recorded, tagged `outcome=success|error`**, so the metrics reflect real-world call volume including abuse/misconfiguration attempts, not just successful usage. Implemented as a new, separate `McpToolMetricsAspect` (`com.synapsemcp.mcp`) rather than folded into `McpToolAccessAspect` — one aspect per cross-cutting concern, matching this codebase's existing convention (`McpToolAccessAspect` for access control, `RateLimitAspect` for rate limiting, this one for observability). Ordered at `HIGHEST_PRECEDENCE` so it wraps *outside* `McpToolAccessAspect` (which has no explicit `@Order`, defaulting to innermost) — this is what makes a blocked call still observable as an "error" invocation.

- [x] Implement MCP error translation adapter (Domain Exception → JSON-RPC Error). **Resolved (Grooming #18/#19):** no separate adapter exists or is needed — `ApiException.getMessage()` already returns client-safe text, and the MCP SDK's own tool-invocation machinery catches any exception thrown from an `@McpTool` method and surfaces it as a clean tool-level error automatically. The only new code is `McpToolInputs`, converting bad-`UUID`/bad-`SearchMode` `IllegalArgumentException`s into client-safe `ApiException`s.
- [x] Ensure Correlation ID generation/propagation in the MCP SSE filter chain. `CorrelationIdFilter` already runs on every request with no path exemptions, confirmed covering `/mcp` in Stage 1 and unaffected by Stage 2.
- [x] Add Micrometer tracking for MCP tool endpoints (Grooming #21). `synapsemcp.mcp.tool.invocations` (Counter, tags `tool`/`outcome`) and `synapsemcp.mcp.tool.duration` (Timer, tag `tool`) via the new `McpToolMetricsAspect`; `synapsemcp.rate_limit.rejections` (Counter, tags `provider`/`kind`) added directly to `ProviderRateLimiter.tryConsume` for the Bucket4j-rejection half of this requirement.
